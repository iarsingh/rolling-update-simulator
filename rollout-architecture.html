Rollout engine — architecture

How it fits together

Two objects and a loop. RolloutEngine is a pure function of fleet state — it never touches infrastructure. Cluster owns the infrastructure and knows nothing about rollout policy. A driver alternates between them once per tick until the engine reports a terminal status.

Runtime flow — one tick

rolling_update_simulator/simulator.py:run() (Python) and simulate() (JS port) both implement this exact cycle.

Engine status — state machine

Owned entirely by RolloutEngine.status; Cluster has no notion of it.

Where each rollout rule lives

Rule 1 — resources

Enforced in _plan_creates: every CREATE is capped by remaining max_surge / resource_capacity headroom before it's issued.

Rule 2 — availability

Enforced in _plan_terminates: a READY instance is only terminated if the fleet has spare ready capacity above min_available.

Rule 3 — unreachable state

record_failure counts new-version health-check failures; past tolerance, plan() flips target back to the old version.

Rule 4 — maintainability

Planning (engine.py), lifecycle simulation (cluster.py), and orchestration (simulator.py) are separate, independently testable modules.
